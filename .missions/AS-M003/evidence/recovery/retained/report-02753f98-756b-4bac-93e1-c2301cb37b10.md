## Confirmed defect and correction

The shared library captures staged HEAD-to-index changes plus independent explicit working-file context. Its private Git runner used `Child::try_wait`, which reaped a normally exited direct leader. Cleanup then sent a negative SIGKILL using that former leader's numeric id. After reaping, that number no longer established the claimed leader identity reservation. Firstmate observed 12 such signals on the real staged capture workflow; no PID reuse or unrelated-process harm was induced.

`src/workspace/git.rs` now observes completion with Linux `waitid(P_PID, ..., WEXITED | WNOHANG | WNOWAIT)`. Observation leaves the leader unreaped, so it reserves its PID/PGID while cleanup signals its owned group. Cleanup then waits/reaps the direct child, before scoped output readers are joined. A completed leader whose descendant holds a pipe therefore remains reserved through the deadline and group cleanup. The finish guard suppresses later group signals, including during Drop. Non-ESRCH group-signal errors and wait failures cannot produce a successful capture.

The main polling loop routes normal completion, output/read failure, observation failure and deadline expiry through this one cleanup path. The Linux siginfo buffer keeps its union opaque and reads only `si_signo`; the host ABI probe verified size 128, alignment 8, leading-field offset 0 and the actual waitid constants. No new dependency, public testing API, process framework, provider route or selector was introduced.

Public capture/configuration behavior and limits remain unchanged: 512 retained inputs, 1 MiB per input, 16 MiB total retained content, 2 MiB per Git inventory, two acquisition attempts, two seconds per Git command and 8 KiB stderr. Comparison-side/context/configuration accounting, object-size admission, relevant-input rechecks and explicit failures remain in place. The limits concern bounded acquisition/content; they do not establish arbitrary kernel-I/O deadlines or a whole-process memory quota.
