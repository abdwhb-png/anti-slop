## Blocking correctness finding

**High — Normalize working executable mode with Git's owner-execute bit.** Source: [src/workspace/acquire.rs:90](worktree/src/workspace/acquire.rs:90), with omission caused by the equality filter at [src/workspace/mod.rs:468](worktree/src/workspace/mod.rs:468). This violates r2's exact working comparisons, relevant file-kind/mode capture and complete-generation obligations, particularly validation criteria 1 and 6.

`Acquisition::working` uses `permissions().mode() & 0o111` to choose `GitMode::Executable`. Stored Git blobs use Git's `100644`/`100755` classification, which follows the owner's executable bit. Consequently two sides are compared using different mode rules.

A real repository was created only under the private review directory. `a.ts` was committed at filesystem mode `0744`; Git records mode `100755`. Its bytes were left unchanged and its filesystem mode changed to `0654`, removing owner execute while retaining group execute. With `core.filemode=true`, actual Git returns:

```text
:100755 100644 c735202 0000000 M\ta.ts
```

The real public `workspace::capture` boundary returns `Ok`, `attempts=1`, **zero changes** for each of `Unstaged`, `Local`, and `Base("HEAD")`. The byte reader still calls the working input executable, so the equality filter discards the real mode transition. Staged remains correctly empty because the index was unchanged. This is a stable successful empty capture that omits a selected change, not an instability, acquisition error or budget limitation.

The inverse counterexample also reproduces: with an index/tree regular file, changing `0644` to group-only `0654` or other-only `0645` leaves Git's comparison empty, but all three working selectors emit a spurious `Regular → Executable` change. A real owner-execute change to `0744` is the positive control. The current code also collapses these different Git working modes into the same observed mode identity. Normal `0755` coverage in the existing suite does not exercise this boundary.

Evidence: [mode-omission-probe.json](final-review-d155e52e/mode-omission-probe.json), [mode-probe.json](final-review-d155e52e/mode-probe.json), and the retained [capture-probe.rs](final-review-d155e52e/capture-probe.rs). The probe imports the real production library; it contains no copy of capture/mode logic. [probe-build.log](final-review-d155e52e/probe-build.log) records its successful frozen-artifact link. [probe-library-identity.json](final-review-d155e52e/probe-library-identity.json) binds the linked library to the matching Cargo dependency artifact and probe bytes. Both fixture repositories and the probe binary remain available under the private directory.

Smallest correction: use the owner-execute bit (`0o100`) when translating working filesystem permissions to `GitMode`; retain the rule in the existing acquisition owner. Add a public capture regression before changing production, asserting exact paths, before/after modes, unchanged bytes and complete results for the three working selectors. Include owner-execute removal with group/other execute retained, and the legitimate no-change group/other-only case. No new abstraction, configuration field or scope decision is needed. ## Git mechanism, acquisition trade-off and design judgment

The negative filter evidence is concrete. `14-0-qualification.log` and `15-0-mechanism-diagnosis.log` observe `helper-ran-filter.probe.process` from real public working capture. The corrected two-file diagnostic reproduces filter execution on the unchanged racy entry. `probe-git-attributes-single-file.json` is the earlier non-reproducing fixture and is not treated as contrary proof. The corrected `probe-git-attributes.json` shows that `--attr-source` suppresses worktree attributes but still executes the filter via `info/attributes`; `17-red-info-attributes.log` confirms that partial remedy fails. The final metadata-only implementation passes the actual working/info/external attribute scenarios in `18-0-metadata-green.log` and stable CI.

The final command planner uses cached logical-index or pinned-tree metadata, current index paths, nonignored untracked paths, and raw stored blobs. It no longer invokes Git working-content diff paths. Rust compares the actual working bytes/modes. No normalization/filter substitution is hidden. Missing required objects fail with lazy fetch disabled; no package/model/fetch work is added. This mechanism is supported by local code and runtime evidence; no fresh external documentation lookup was needed to establish it.

The wider acquisition footprint is explicit and material: unchanged comparison candidates are read to prove equality. They consume limits and remain bound observations in capture identity, while being omitted from returned changes and never becoming inferred analyzer context. Source exclusions reject required candidates before reading even when a later comparison might have shown equality. A tiny edit can therefore fail explicitly in a large baseline. This is consistent with the approved finite-capture boundary and documented trade-off, not a claim that large repositories are qualified.

The proposal uses 512 admitted observations/roles, 1 MiB per content input, 16 MiB total admitted content per attempt, 2 MiB per inventory, at most two attempts, 512 entries per caller list, 4,096-byte paths/configuration arguments and 8 KiB Git stderr. Working capture holds bounded baseline/index/untracked inventories plus at most one recheck inventory, and one extra bounded content input during verification. Shared Arc data is conservatively counted per role. Total allocator/compiled-config/Git-internal/kernel memory is not capped by these numbers. Arbitrarily blocked filesystem/kernel I/O is not covered by the Git wait deadline.

The design keeps selection, generations and rename attribution in `workspace`, descriptor-safe reads/accounting in its private acquisition module, and Git command/blob/process lifetime in its private Git module. Configuration policy is not duplicated in workspace or CLI. The public interface hides substantial acquisition/retry/lifetime complexity without a forwarding-service chain, generic plugin/store framework, universal AST or new crate. The long `capture` function follows one coupled attempt lifecycle; moving its steps into shallow wrappers would not itself improve information hiding. I found no separate architecture defect requiring a refactor. The concrete mode rule belongs in the existing acquisition module and should be corrected there.
