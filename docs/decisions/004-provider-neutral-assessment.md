# ADR-004: Provider-neutral assessment

## Status

Accepted. The judge boundary and provider integrations are not implemented.

## Date

2026-09-22

## Context

Jev is the initial intended judge, but the user plans to collect enough evidence to evaluate and fine-tune a better replacement. Coupling rule meaning, confidence or training records to Jev would make replacement a product redesign. Excessive model calls would also conflict with deterministic operation and resource constraints.

## Decision

The Rust application owns versioned evidence and assessment meaning. A request identifies its candidate, rule definition/version, exact evidence, coverage and the question to resolve. Judge adapters own provider rendering, transport and translation into the common outcomes; they cannot privately redefine a rule.

Keep separate:

- **Execution:** completed, failed, cancelled, timed out or otherwise incomplete.
- **Assessment:** supports the issue, rejects it, or finds evidence insufficient.
- **Policy:** the action justified by enabled rules and their qualified scope.
- **Provenance:** provider/model identity, renderer/configuration, exact input/output and observed usage/latency.

Retain raw provider scores or distributions as provider-specific observations. Do not invent a universal confidence scale or transfer thresholds between models or prompts. Unknown changes to the effective model identity invalidate assumptions about earlier qualification.

Render the same canonical evidence into the format suitable for the selected provider. TOON/JSON CLI selection does not choose a model prompt format. Deterministic extraction and candidate selection constrain which questions need a model; the model does not own the analysis workflow or execute repository instructions.

Treat source code and comments as input data. Validate returned outcomes and evidence references. Diagnostics distinguish actual observations from attributed assessments; an explanation generated by a future model is not additional source evidence. A provider incapable of generating rationale must not be presented as having done so.

## Alternatives Considered

- **Jev response types as domain and dataset types:** faster initial plumbing, but contaminates rule semantics, policy and replacement evaluation with provider assumptions.
- **One prompt or score threshold for every provider:** superficially uniform, but does not establish equivalent capabilities or calibration.
- **An autonomous model controlling extraction and policy:** creates unnecessary variability and obscures bounded execution, provenance and failures.

## Consequences

A replacement must pass the neutral contract, independent held-out evaluation and calibration, then non-blocking comparison on real workloads. Requalify affected blocking policies and retain a known qualified configuration for rollback. Agreement with Jev's own labels is not independent evidence of quality.

Contract tests must cover malformed responses, invalid references, unsupported capabilities, provider failure and ambiguous retries. Apply the whole-phase deadline in [ADR-007](007-performance-budgets-and-qualification.md); retries and fallbacks cannot reset it. Persist execution attempts according to [ADR-005](005-local-evidence-store-and-dataset-exports.md). A local transaction cannot prove that an uncertain remote request never executed.

## Evidence and Remaining Qualification

Records the user's explicit model-replacement requirement and the [historical judge design](../brainstorming-decisions/2026-09-22-anti-slop-design.md#replaceable-judge-contract).

Exact provider capabilities, schemas, model identities, request rendering and routing configuration remain to implement and qualify. The name “Laya” has not been resolved to a particular model or training interface; no contract depends on guessing it. This decision does not authorize paid inference or implement model training.
