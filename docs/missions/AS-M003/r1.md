# AS-M003 — Coherent selected sources

Status: approved for local document preparation on 2026-11-15. The execution state remains draft: implementation, worker/reviewer launches, installation, commits and publication are not authorized. This file is the authoritative AS-M003 contract; the earlier private draft is preparation history only. Existing approved mission records remain unchanged.

## Outcome

Given exactly one existing product selector and an explicit list of supporting context files, the shared Rust library captures the intended changes and the requested context as independently attributable, owned source inputs. The caller can inspect the exact captured bytes after the original files change, identify the comparison and effective configuration, and distinguish a complete capture from unstable, excluded or unavailable input.

This supplies the source boundary needed by later evidence and analysis work. It does not produce an analysis verdict, a durable run or a qualified clean result.

## Decisions and Constraints

- Preserve PRD selection semantics and ADR-002, ADR-007 and ADR-008. Use English for project interfaces and artifacts.
- Accepted in this preparation: supporting context comes from an explicit caller-provided file list. Discovering transitive dependencies belongs to the later analyzers.
- Keep selected changes and context distinct even when they name the same path at different versions. Identify their actual origins and generations.
- Retain actual captured bytes. Hashes, Git commits, timestamps and path names alone are insufficient substitutes.
- Reuse the configuration owner. One capture must not silently combine several file versions of the selected configuration. Preserve AS-M002 configuration selection and origin semantics.
- The internal representation is an implementation choice. It must keep captured inputs independent of subsequent edits, respect explicit finite resource limits, and introduce no hard links or symlinks back to mutable source.
- Existing scope, delivery and execution authorities are separate. The standing execution mode is coordinated; no assignment is authorized by this draft.

## Scope

Implement source selection and capture through the shared Rust library, owned by `workspace`, with only the necessary configuration integration and integration tests. Keep the existing configuration CLI behavior.

| Request | Comparison and selected bytes |
| --- | --- |
| Staged | HEAD to index; select index content. Exclude worktree-only edits and untracked files. |
| Unstaged | Index to working files; include nonignored untracked files. Exclude staged-only changes whose index and working bytes agree. |
| Local | HEAD to working files; include nonignored untracked files. |
| Explicit base | Resolve the supplied reference once and compare that exact commit directly to working files, including local and nonignored untracked changes. Never substitute merge-base. |

Capture additions, deletions, rename attribution, relevant file kinds and both comparison sides where needed to reconstruct the selection. Deletions retain their available prior bytes; absence is not an empty file. A valid empty selection is distinguishable from a failed acquisition.

Capture only requested context and explicitly identified configuration/dependency inputs. Do not infer an import graph, package contents or a complete dependency environment. Each supporting input records its actual source view; no silent origin fallback is permitted.

Respect Git ignore rules for untracked inputs and declared capture exclusions. Disclose excluded requested scope. Do not reinterpret configuration override exclusions as repository-wide source exclusions or add a competing configuration format.

Preserve the analyzed repository's files, index and references. No analysis operation may run project helpers, filters, external diff tools, install packages, fetch missing repository data or contact a model. Unsupported Git states, file kinds and required transformations must be explicit rather than silently reducing coverage.

Exclude native analyzers and overlays, rule evaluation, model calls, storage/export, caches, resident sessions, a new CLI command, public schema hosting, and changes to previous mission history.

## Validation Contract

Use real temporary Git repositories and the production Rust capture/configuration modules at their consuming public boundary. Mock only external or nondeterministic boundaries where needed for a controlled failure. Begin each production behavior change with an intended failing test; preserve its RED and GREEN evidence.

Required behavioral evidence:

1. A fixture with distinct base, merge-base, HEAD, index and working bytes proves all four comparisons. Include a staged-only file and a nonignored untracked file; assert exact selected paths, roles, comparison identities and bytes, not just success.
2. Working-tree context for a staged selection retains a separate identity and cannot replace staged bytes. After capture, editing or removing original source/configuration leaves the earlier capture inspectable and unchanged.
3. Additions, deletions, renames, ignored inputs, explicit exclusions and a valid empty selection remain distinct. Required excluded or unavailable scope cannot become an unexplained empty or clean result.
4. Missing/conflicting selection, unresolved base, a required absent HEAD, unmerged index, unreadable required input and unsupported repository states produce explicit failures before downstream work. No branch default or implicit scope repairs an invalid request.
5. Path handling covers spaces, tabs/newlines, duplicates, traversal and symlink escapes. Preserve identity without lossy conversion; reject unsupported names or kinds explicitly. Do not read an escaped source target. Preserve the separately authorized external configuration behavior of AS-M002.
6. Controlled changes to source, inventory, index or configuration during acquisition either yield a capture justified by the documented checks within a finite attempt bound or return an explicit instability failure. State the achieved observation scope; do not claim global atomicity or perpetual freshness.
7. Captured byte ranges refer to the correct role, generation and exact bytes, including Unicode, empty files and end-of-file boundaries. Invalid or unbound ranges fail. No universal language AST or native source mapping is required.
8. Configuration resolution for multiple paths uses one captured configuration version and preserves existing policy/origin behavior. Changed configuration produces a new effective identity.
9. Finite file-count, per-file byte, total retained byte and acquisition-attempt limits are documented and tested at their boundaries. A limit failure cannot be presented as a complete capture. Record proposed limits and their measured implications before acceptance.

Record capture timing, retained file/byte counts and whole owned-process resource observations on the controlled scenarios, including one-file and up-to-five-file/200-changed-line cases. Retain commands, host/cache conditions and measurement limitations. There is no existing capture implementation for a before/after baseline; compare the implemented scenarios transparently. These measurements do not qualify ADR-007's later complete analysis budgets. Frozen real-project and native overlay qualification remain later work.

Run the focused capture and affected configuration tests during implementation. At the stable candidate, run the repository's documented CI verification and structural checks required by the selected delivery contract, recording actual results and unavailable prerequisites. Documentation consistency checks replace application RED tests for documentation-only edits.

Independent final validation must examine the full mission outcome, cumulative diff, failure evidence, resource observations and remaining limits. A structural validator result or implementer's report is not independent acceptance.
