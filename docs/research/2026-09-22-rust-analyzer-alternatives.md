# Rust semantic engine alternatives

Research date: 2026-09-22. This follows the [initial language qualification](2026-09-22-language-qualification/README.md). It is source and documentation research, not a new performance experiment.

## Decision and conclusion

**D9 — Keep rust-analyzer provisionally.** The user accepts its observed cost for the current small number of Rust projects and wants replacement to remain possible. This accepts the present trade-off; it does not establish a universal memory budget, approve an always-resident process, or qualify every rule and Rust project shape.

No researched alternative demonstrates the combination of broader established adoption, an equally suitable standalone integration, sufficient semantic coverage and lower measured cost on our workload. Keeping the already exercised rust-analyzer path therefore has the lowest demonstrated integration uncertainty. This is an assessment for Anti-Slop, not a claim that rust-analyzer is the fastest, most complete or most memory-efficient Rust engine.

Rust Glancer is a real alternative worth reconsidering. Its saved-file workflow is compatible with D4, so it should not be rejected merely because its unsaved-buffer support is weaker. Its completeness and resource trade-offs still require local qualification before replacement.

## Rust Glancer: why it is promising, and why not switch now

The release inspected is **v0.2.0**, published on GitHub on **2026-09-01**, source commit `7737db379d16f0de8c6d917335f288780ad6d26d`. The project was publicly introduced in August 2026. Its release-specific source confirms both the supported LSP operations and the intentionally narrower scope; this is more than a syntax-only parser. [Release](https://github.com/rust-glancer/rust-glancer/releases/tag/v0.2.0), [introduction](https://rust-glancer.github.io/blog/hello-world/).

The author's v0.2.0 benchmarks distinguish low idle usage from substantial initial indexing peaks. For example, the published Tokio row reports **50.4 MiB idle**, **1,538.3 MiB peak** and **4.638 seconds full indexing**; Bevy reports **75.5 MiB idle** and **7,936.4 MiB peak**. Idle was measured after indexing, restarting and making a hover query. These are author measurements on other projects and hardware, not values reproduced here and not comparable with our 203-file fixture. The post also describes a lower-peak mode with an indexing-time trade-off. [Benchmark methodology and results](https://rust-glancer.github.io/blog/0-2-0/).

For our post-agent saved-file workflow, a persistent index and lower idle residency could be useful. However, an incomplete reference/type result can distort a design assessment or the evidence recorded for a future model. The released documentation explicitly permits outdated build-script artifacts and does not automatically refresh them on every ordinary reindex. Those boundaries need to be represented, not treated as a complete current project. Our initial rust-analyzer probe also disabled procedural macros and build scripts: their absence alone is not a fair reason to reject Glancer while accepting that probe.

Aleksey Kladov's independent technical commentary welcomes Glancer and discusses more compact syntax representations and disk-backed dependency information for rust-analyzer. That supports treating memory architecture as improvable. It is expert analysis, not an independent apples-to-apples benchmark or a guarantee that a replacement will preserve our coverage. [Commentary, 2026-08-21](https://matklad.github.io/2026/08/21/rust-glancer.html).

## Why rust-analyzer remains the current choice

- **RA1 — Established integration:** the Rust project adopted it as the RLS replacement, Zed uses it as its default Rust server, and the SCIP Rust wrapper also depends on it. These are concrete ecosystem integrations; GitHub stars are not used as user counts. [Rust project](https://blog.rust-lang.org/2022/07/01/RLS-deprecation/), [Zed](https://zed.dev/docs/languages/rust), [SCIP wrapper](https://github.com/sourcegraph/scip-rust).
- **RA2 — Relevant observed capability:** our actual probe exercised workspace navigation, traits, a declarative macro, cfg changes and dependent updates. It supplies a known baseline for subsequent rule qualification. It does not establish complete reference/type coverage or correctness for all Rust programs. [Local results](2026-09-22-language-qualification/README.md).
- **RA3 — Suitable boundary:** its LSP interface is stable relative to the explicitly unstable internal IDE API. This helps contain version and process management inside the Rust adapter. LSP extensions and rich type extraction still need their own versioned contracts. [Pinned architecture](https://github.com/rust-lang/rust-analyzer/blob/2026-09-14/docs/book/src/contributing/architecture.md).
- **RA4 — Accepted present cost:** the user accepts the measured footprint for limited Rust use. Optimizing that dependency is less urgent than proving the first complete evidence/rule/record path. This is a user trade-off, not a claim that Rust semantic analysis inherently requires roughly 500 MiB.

For later Pi integration, demand-driven startup, reuse during active Rust work and bounded idle retention are scheduling candidates to measure. Stopping the process trades retained memory for another startup; it does not eliminate analysis cost. No daemon, timeout or numeric resource policy is selected here.

## Replacement boundary

Keep rust-analyzer-specific requests, IDs, snapshots and process lifecycle inside the language adapter. Rules and dataset records depend on the existing evidence contract, with analyzer/version/configuration provenance and explicit coverage. Do not promote analyzer output into human-confirmed labels.

Replacement should compare equivalent saved-source workloads, facts and rule outcomes; capture first indexing, warm updates, restart, peak and idle process-tree memory; verify source/configuration/dependency invalidation; and preserve missing-analysis states. A new engine can qualify only the capabilities it actually supports. Sharing LSP is helpful but does not make semantic behavior or extension coverage interchangeable.

## Research scope and verification

Exa and web search supplied discovery and operational perspectives; DeepWiki supplied navigation leads. Decision-critical Glancer claims were checked in a local read-only checkout of its release, and Dylint/rust-analyzer contracts against versioned source. Official GitHub metadata was queried through `gh` on 2026-09-22: rust-analyzer's latest published release was 2026-09-21, Glancer's v0.2.0, and Dylint's v6.0.4. These observations do not change our tested rust-analyzer pin of 2026-09-14.

No dependencies were installed and no alternative analyzer was executed. Glancer's performance advantage on our workload, population-level usage, long-session behavior and replacement coverage remain unverified. The earlier qualification measurements and their raw archive remain unchanged.
